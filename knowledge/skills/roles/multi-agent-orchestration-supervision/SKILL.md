# Multi-Agent Orchestration, Supervision & Drift Governance

This skill establishes the methodology for supervision, coordination, and operational quality control over fleets of autonomous agents in hierarchical and distributed multi-agent systems.

---

## 🎯 1. Fundamental Principles of the Supervisor

1. **Intent Grounding**:
   - Every workflow begins by extracting and fixing the user's original problem into an explicit intent contract.
   - The contract must contain: Primary Objective, Non-Negotiable Constraints, Expected Deliverables, and Stop Criteria.
2. **Routing Before Delegation (mandatory)**:
   - Choose the subagents through the deterministic router, not by guess. Run `python3 scripts/coacus_route.py "<prompt>" --max-slots` and start from the ranked candidates with their matched terms; the `--max-slots` cap ties the proposal to the governor's free slots.
   - Honor an explicit user selection by validating it: `python3 scripts/coacus_route.py --agents name1,name2`. An unknown name is an error with suggestions, never a silent drop.
   - When the router returns nothing, browse with `--list` and select manually; never invent an agent name.
3. **Active Execution Vigilance (Observation Loop)**:
   - The supervisor does not perform the domain's hands-on work, but monitors the tool calls, messages emitted, and files modified by the subagents.
4. **Principle of Minimum Efficient Intervention**:
   - Adjust first with contextual guidance (*re-prompting*).
   - Contain second (limit permissions or pause execution).
   - Terminate (*kill*) only when drift persists, there is an infinite loop, or there is operational risk.

## 🔍 2. Taxonomy of Drift (Agent Drift)

The supervisor must continuously monitor the following failure modes:

| Drift Category | Observable Symptom | Typical Root Cause | Recommended Action |
| :--- | :--- | :--- | :--- |
| **Role Drift** | A research subagent trying to edit production files; a frontend agent refactoring database migrations. | Boundary hallucination or a permissive system instruction. | Immediate blocking of the action and restatement of the role's restricted scope. |
| **Scope Drift** | A subagent expanding the task to refactor unrequested modules or create unrequested features. | Premature optimization or loss of intent grounding. | Reprompt to abort side tasks and focus strictly on the goal. |
| **Loop / Deadlock Drift** | A subagent repeating the same tool call with identical parameters or cycling with no progress. | Failure to interpret tool errors or polluted context. | Cancel the operation, clean the context, and provide an alternative strategy. |
| **Hallucinated Progress** | A subagent reporting completion status without the physical files or assertions having been validated. | Sycophantic response or absence of a validation oracle. | Reject the status, demand concrete test/execution evidence. |

## 🛑 3. Gradual Containment and Kill-Switch Protocol

When an agent shows drift, the supervisor applies a 3-level response scale:

### Level 1: Guidance Intervention (Nudge & Realignment)
- **Corrective Message**: Issue a direct correction command citing the original intent.
  ```text
  [DRIFT ALERT] Your last action diverged from the initial objective.
  Current Objective: <anchored-intent>
  Incorrect Action: Attempt to refactor code outside the scope.
  Instruction: Stop this change and strictly resume the delegated task.
  ```

### Level 2: State Containment and Rollback (Quarantine & Rollback)
- Revert files or incorrect modifications generated by the drifting subagent.
- Clear the contaminated recent memory or resend a lean summary of the task.

### Level 3: Forced Termination (Kill-Switch)
- If the agent insists on the wrong behavior after a Level 1 intervention:
  1. Execute the immediate shutdown call (`manage_subagents: kill` or task cancellation).
  2. Record the drift log for post-mortem auditing.
  3. Reassign the demand to a fresh, zeroed instance or take over the conduction yourself.

## 📡 4. TOON Communication Protocol with Heartbeat

When communicating with delegated subagents, the supervisor requires structured telemetry sent via the **TOON** protocol:

```text
@FROM: <subagent>
@TO: orchestrator
@STATUS: <OK | BLOCKED | DRIFT_DETECTED | DONE>
@CTX: <anchored-task-id>
@PROGRESS: <summary-of-progress-made>
@NEXT_ACTION: <next-intended-call>
```

If a subagent fails to respond to the supervisor in a timely manner or emits actions that diverge from the `@CTX`, the termination process is triggered preventively.

## ⛓️ 5. Concurrency Governance and Rate-Limit Prevention

The supervisor is responsible for protecting the session from provider quota overruns (`429 Too Many Requests`, `RPM/TPM exceeded`, `tokens per minute`). To do so, it keeps concurrency under control:

### 5.1 Subagent Ledger

Keep a live record of each subagent's state:

| State | Meaning |
| :--- | :--- |
| `ACTIVE` | Running in parallel right now. |
| `QUEUED` | Delegated, but waiting for a concurrency slot to open. |
| `DONE` | Completed successfully. |
| `FAILED` | Failed without a rate-limit symptom (logic, loop, drift). |
| `PAUSED` | Failed due to rate-limit; awaits relaunch when capacity frees up. |

### 5.2 Concurrency Cap

- **Role limit**: never leave more than **5 active agents** at once **counting the supervisor itself** (that is, supervisor + at most **4 subagents** in `ACTIVE`). Respect any lower limit resolved by the runtime governor.
- To delegate, compute `active = 1 (you) + number of ACTIVE subagents`. While `active >= 5`, do **not** spawn new subagents: move the task to `QUEUED` and wait for a `DONE`/`FAILED`/`PAUSED` signal to release the next one from the queue (FIFO).

### 5.3 Rate-Limit Failure → Kill, Wait, and Relaunch

Rate-limit symptoms: `429`, `HTTP 429`, `Too Many Requests`, `Rate limit`, `Quota exceeded`, `RPM exceeded`, `TPM exceeded`, `tokens per minute exceeded` (in error messages, response headers, or tool status).

When one of these symptoms is detected on an active subagent:
1. **Kill** the instance immediately (kill-switch) and mark it `PAUSED`, **preserving** the subtask description and its `@CTX` for retry.
2. **Wait** while the total active count (you + other ACTIVE) remains at 5; do not relaunch yet.
3. When the total active count drops **below 5**, **relaunch** the paused task (a fresh zeroed instance) applying *exponential backoff* between attempts: ≈2s on the 1st, 4s, 8s, 16s, 32s, up to a 60s ceiling. Reset the task state to `ACTIVE` on relaunch.
4. Once a reasonable limit of consecutive attempts is exhausted (e.g., 5), report the definitive `FAILED` to the user and continue with the rest of the queue.

### 5.4 Retry Scope

- **Only** failures with a rate-limit symptom enter the `PAUSED`/retry flow.
- Any other failure (drift, loop, logic error) follows the standard **Level 1/2/3 protocol of section 3**, being treated as `FAILED` with no automatic relaunch.

### 5.5 Executable Mechanism (not just instructional)

The role limit above is an instruction. The runtime governor enforces the scope ledger's effective slot limit, which can differ from the role limit:

- **Governor** (`scripts/coacus_governor.py`): the slot ledger. `acquire` blocks (queues) when the effective cap is saturated; `fail` marks the caller `PAUSED` for retry. Initial limits resolve from model, harness and environment settings; the fallback for an unlisted scope is 6. An existing ledger persists its cap: a higher requested cap can raise it, but lowering configuration alone does not lower it. For a durable decrease, lower the relevant configuration as well as using `set-max`; a later caller with a higher resolved cap can raise it again. Inspect the effective value with `status`.
- **OpenCode gate** (`~/.config/opencode/plugins/coacus-governor.js`): intercepts `task`, acquires a slot before the spawn, releases/marks it after, and parks a caller as `PAUSED` when it sees a rate limit.
- **Antigravity hook** (`~/.gemini/config/hooks.json`, key `coacus-governor`): calls `scripts/coacus_governor.py` on the pre-spawn hook of every subagent dispatch and releases on the post-spawn hook.

## 🧮 6. Quantitative Tool-Call Caps and Mentor Supervision Loop

Beyond subagent process counts, the supervisor actively enforces tool-call budgets and sliding-window loop detection:

### 6.1 Differentiated Tool-Call Budgets
- **Deep Execution Agents** (`general`, `backend-developer`, `pentester-agent`): `MAX_GENERAL_AGENT_TOOL_CALLS = 100`.
- **Auxiliary & Refinement Agents** (`code-explorer`, `web-researcher`, `subtasks-refiner`): `MAX_LIMITED_AGENT_TOOL_CALLS = 20`.

### 6.2 Sliding-Window Loop Detection
- **`same_tool_limit` (3–5 calls)**: If an agent invokes the same tool with identical or near-identical arguments 3 to 5 times consecutively without new outputs or error resolution, trigger an immediate Level 1 drift intervention.
- **`total_tool_limit`**: If an agent consumes 80% of its budget without generating verifiable artifacts or passing tests, pause the agent and evaluate progress using the `<mentor_analysis>` checklist.

### 6.3 The `<mentor_analysis>` Progress Checklist
Before redelegating a task, approving completion, or releasing an agent:
```text
<mentor_analysis>
1. Artifact Verification: Has the subagent produced physical files, test runs, or concrete evidence?
2. Loop Check: Is the subagent repeating tool invocations or stuck in an unproductive cycle?
3. Scope Adherence: Are modified files strictly within the declared bounded context?
4. Context Completeness: Can the current question or step be resolved immediately from context?
5. Budget Depletion: Has the agent consumed >80% of its tool budget without measurable progress?
6. Objective Grounding: Is the proposed next step aligned with the user's root objective?
</mentor_analysis>
```

## 🌐 7. English-First & Dual-Channel Language Governance

To maintain semantic density, eliminate token waste, and prevent translation loss during cross-agent handoffs and memory retrieval:

1. **Technical Wire & Memory Channel (100% `en`)**:
   - All TOON handoff fields (`@SUMMARY`, `@ACTION_NEEDED`, `@CTX`), tool call parameters, vector search queries, knowledge graph triples, and internal scratch notes MUST be in **English (`en`)**.
2. **Human Communication & Reporting Channel (`en` canonical; `en | pt-BR | es` supported)**:
   - When presenting final executive reports, asking user clarification, or providing status summaries to human stakeholders, the agent standardizes on the three core supported languages: **English (`en`)** as canonical default, **Brazilian Portuguese (`pt-BR`)**, and **Spanish (`es`)**.

## 🔐 8. Cryptographic Evidence Receipt Chain Integration

For auditability and non-repudiation in offensive security, GRC, or critical code deliveries, agents emit an Ed25519-signed, hash-linked DAG of execution receipts:

```text
flow_start -> task_created -> subtask_started -> toolcall_finished -> artifact_recorded -> report_created
```

- Each receipt records: `receipt_id`, `parent_receipt_ids`, `event_type`, `input_hash` (SHA-256), `output_hash` (SHA-256), and `artifact_hashes`.
- Offline verification fails closed: any broken link or mismatched payload signature invalidates downstream findings.
